# Doro ERP k6 부하 테스트 시나리오

> 개정 이력
> - v2 — 시나리오 11개 → 9개로 통합, 실행 규칙(3.2) 신설, 결제 부하 테스트 제외
> - v2.1 — 데이터 초기화 절차(3.3) 추가
> - v2.2 — 시작 전 준비물 체크리스트(0장) 추가
> - v2.3 — 구현 확인 결과 반영 (규칙 2·4, 시나리오 3·5, 신설 11장)
> - v3 — 시나리오 10(한계 탐색) 신설, 매장 주문 기본 제외 (규칙 8)

## 0. 시작 전 준비물

아래 6개가 채워지기 전에는 부하 테스트를 시작하지 않는다.

| # | 항목 | 값 / 담당 | 상세 | 완료 |
| ---: | --- | --- | :---: | :---: |
| 1 | 기준 피크 처리량 (100%) | **`____` RPS** | 4장 | ☐ |
| 2 | 기준 피크 동시 사용자 | **`____` VU** | 4장 | ☐ |
| 3 | 초기 데이터 생성 스크립트 | `____` | 3.3.4 | ☐ |
| 4 | Redis 키 삭제 명령 | `____` | 3.3.3 | ☐ |
| 5 | 누적 데이터 삭제 SQL | `____` | 3.3.6 | ☐ |
| 6 | 삭제 주기 | `____` | 3.3.2 | ☐ |

**부분 실행 조건**

- 3~6번만 준비되면 → 시나리오 1~6, 10 실행 가능
- 1~2번까지 확정되면 → 시나리오 7~9 실행 가능
- 3번(초기 데이터 생성)이 없으면 → **어떤 시나리오도 실행 불가**

1~2번은 시나리오 1~6의 실측 결과를 보고 정해도 된다. 3번이 최우선 작업이다.

## 1. 목적

Doro ERP의 실제 사용 흐름을 기준으로 동시 요청이 증가할 때 다음을 확인한다.

- POS·키오스크의 주요 API가 정상 응답하는지
- 주문 생성부터 조리 완료·주문 완료까지 핵심 흐름의 처리 성능
- 동일 요청 재전송 시 중복 데이터가 생기지 않는지
- 순간 집중과 장시간 운영에서 오류율·응답시간·처리량
- Edge 및 각 서비스(Store Access, Commerce, Payment, Queue, Audit)의 병목 구간

**범위에서 제외하는 것**

- 실제 결제사 승인 (외부 비용·승인 위험). 결제 API는 단일 사용자 기능 확인까지만 하고 부하는 걸지 않는다. → 9장
- 운영 환경. 부하 테스트 전용 환경에서만 실행한다.

## 2. 용어

문서를 읽는 데 필요한 최소한의 용어만 정리한다.

| 용어 | 뜻 |
| --- | --- |
| VU (Virtual User) | k6가 만들어내는 가상 사용자 1명 |
| 닫힌 모델 (`ramping-vus`) | 사용자 수를 고정. 응답을 받아야 다음 요청을 보내므로, 서버가 느려지면 요청량도 같이 줄어든다 |
| 열린 모델 (`ramping-arrival-rate`) | 초당 요청 수를 고정. 서버가 느려져도 요청이 계속 들어와 뒤에 쌓인다 |
| 멱등성 | 같은 요청을 몇 번 보내도 결과는 한 번만 반영되는 성질. 버튼 연타·자동 재시도 대비 |
| 기준 부하 (100%) | 이 문서에서 "피크"로 정의한 목표 처리량. → 4장 |
| 의도된 오류 | 테스트가 일부러 유발하는 4xx. 실패율 집계에서 제외한다 |

**부하 모델을 왜 구분하는가**

닫힌 모델은 서버가 느려지면 부하도 같이 줄어들어 한계를 못 찾는다. 실제 피크 시간은 열린 모델에 가깝다. 따라서 **쓰기 중심 시나리오는 열린 모델, 화면 조회 중심 시나리오는 닫힌 모델**을 쓴다. 각 시나리오에 어느 쪽인지 명시했다.

## 3. 공통 전제 조건

### 3.1 환경과 데이터

- 부하 테스트 전용 환경과 전용 업체를 사용한다.
- 테스트 업체에 매장, 점주·매니저·직원 계정, 카테고리, 판매 상품, 활성 테이블을 미리 등록한다.
- 테스트 데이터가 운영 통계와 섞이지 않도록 별도 업체 코드를 사용한다.
- 실행할 때마다 실행 ID(`RUN_ID`)를 발급하고, 생성되는 주문·대기 데이터의 메모 또는 식별 가능한 필드에 기록한다.

### 3.2 실행 규칙 (스크립트 작성자 필독)

아래 8개는 지키지 않으면 **결과 자체를 읽을 수 없게 되는** 항목이다.

**규칙 1. 모든 요청에 고정 `name` 태그를 붙인다**

k6는 URL이 다르면 다른 지표로 집계한다. `/api/v1/orders/{orderId}`를 그대로 두면 주문 1건마다 별개 지표가 생겨 p95를 낼 수 없다.

```js
http.get(`${BASE}/api/v1/orders/${orderId}`, {
  tags: { name: 'order_detail' },   // 필수
});
```

태그 이름은 아래 표를 그대로 쓴다. 시나리오별 임의 작명 금지.

| 태그 | API |
| --- | --- |
| `login` | `POST /api/v1/auth/login` |
| `menu` | `GET /api/v1/catalog/menu` |
| `order_list` | `GET /api/v1/orders?businessDate=...` |
| `order_create` | `POST /api/v1/orders` |
| `order_detail` | `GET /api/v1/orders/{id}` |
| `order_complete` | `POST /api/v1/orders/{id}/complete` |
| `order_cancel` | `POST /api/v1/orders/{id}/cancel` |
| `table_list` | `GET /api/v1/tables` |
| `kiosk_activate` | `POST /api/v1/kiosk-auth/activate` |
| `entry_create` | `POST /api/v1/queues/entry` |
| `entry_list` | `GET /api/v1/queues/entry?businessDate=...` |
| `entry_transition` | `POST /api/v1/queues/entry/{id}/{enter\|cancel\|no-show}` |
| `fulfillment_list` | `GET /api/v1/queues/fulfillment` |
| `fulfillment_ready` | `POST /api/v1/queues/fulfillment/{id}/ready` |

**규칙 2. 인증은 `setup()`에서 1회만 수행하고 재사용한다**

비밀번호 해싱은 의도적으로 느리게 설계된 연산이다. 매 반복마다 로그인하면 서버 CPU가 인증에 소모되어, 주문 성능이 아니라 로그인 성능을 측정하게 된다.

- POS: **VU당 1회** 로그인하고 그 세션을 계속 재사용한다. (`setup()`의 쿠키는 VU로 전달되지 않으므로 setup에서 로그인해도 VU가 다시 로그인해야 한다.)
- 키오스크: **VU당 1회** 기기 활성화.
- **직원 세션과 키오스크 인증을 한 VU에서 섞지 않는다.** `SESSION` 쿠키와 `DORO_KIOSK_DEVICE` 쿠키가 동시에 존재하면 `401 AMBIGUOUS_AUTHENTICATION`이 반환된다. 혼합 부하에서는 executor를 분리한다.
- 비-GET 요청은 `XSRF-TOKEN` 쿠키 값을 `X-XSRF-TOKEN` 헤더에 그대로 넣는다.
- 예외: 시나리오 1은 로그인 자체가 측정 대상이므로 반복 로그인한다.
- 세션 만료 시 재로그인하는 처리를 넣되, 재로그인 발생 횟수를 별도 카운터로 기록한다.

**규칙 3. VU끼리 같은 데이터를 건드리지 않는다**

여러 VU가 같은 목록에서 항목을 골라 상태를 바꾸면 서로 충돌해 409/404가 대량 발생한다. 이는 서버 결함이 아니라 스크립트 결함이지만 실패율에는 똑같이 잡힌다.

- 상태 변경 대상은 **해당 VU가 직접 생성한 항목**으로 한정한다.
- 테이블처럼 미리 만들어둔 자원은 풀 전체를 고르게 돌려 쓴다. 필요한 수는 규칙 8의 식으로 계산한다.
- 공유 자원 경합 자체를 검증하려는 경우(시나리오 6)는 별도 시나리오로 분리하고, 그때의 충돌 응답은 규칙 4에 따라 처리한다.

**규칙 4. 의도된 오류는 실패율에서 제외한다**

아래는 **거절되는 것이 정상**인 요청이다. 기본 실패 판정에서 빼고 별도 커스텀 지표로 센다.

| 상황 | 실제 응답 |
| --- | --- |
| 비활성 테이블로 `DINE_IN` 주문, 유형별 `tableId` 규칙 위반 | **400** `VALIDATION_FAILED` |
| 같은 멱등키 + 다른 본문 | **409** |
| 멱등 처리 중 동시 요청 | **409** |
| 이미 종료된 대기의 재전이 | **409** `STATE_CONFLICT` |
| 이미 준비완료된 조리 항목 재처리 | **409** |

멱등키 충돌의 `code` 문자열은 계약 문서(`IDEMPOTENCY_KEY_REUSED`)와 구현(`IDP_CONFLICT`)이 다르다. **`code`로 판정하지 말고 HTTP 409로만 판정한다.**

```js
const res = http.post(url, body, { tags: { name: 'order_create' }, responseCallback: expected });
// expected: http.expectedStatuses(200, 201) 또는 시나리오별 허용 코드
```

**규칙 5. 쓰기 요청마다 `Idempotency-Key`를 붙인다**

- 서로 다른 업무 요청에는 서로 다른 키. 형식은 `{RUN_ID}-{난수}-{VU}-{ITER}-{용도}` 권장. VU·반복 번호만 쓰면 회차를 다시 돌릴 때 같은 키가 재생성되어, 이전 회차의 키가 남아 있으면 첫 요청이 재생 처리된다.
- 멱등성 검증(시나리오 6)에서만 의도적으로 같은 키를 재사용한다.

**규칙 6. 주문 유형별 필드 규칙**

- `DINE_IN` → 활성 `tableId` 포함
- `TAKEOUT` → `tableId` 미포함

**규칙 7. 회차 시작 전 데이터를 초기화한다** → 상세는 3.3

**규칙 8. 매장 주문(`DINE_IN`)은 기본적으로 만들지 않는다**

테이블은 **한 번에 주문 1건**만 받는다. DB에 부분 유니크 인덱스로 강제되어 있고, 같은 테이블 요청은 `SELECT ... FOR UPDATE`로 직렬화된다. 게다가 주문을 완료·취소해도 해제는 즉시가 아니라 **최대 30초 뒤**에 일어난다(11장 참고).

즉 매장 주문의 처리량은 서버 성능이 아니라 **테이블 수 ÷ 해제 주기**로 결정된다.

```
테이블 500개 ÷ 35초 ≈ 초당 14건   ← 이 이상은 구조적으로 불가능
```

이 상태로 섞어 돌리면 **서버 성능이 아니라 테이블 회전율을 측정하게 된다.** 따라서 기본값은 포장(`TAKEOUT`) 100%로 두고, 매장 주문은 필요할 때만 켠다.

| 상황 | 설정 |
| --- | --- |
| 기본 (처리량 한계 찾기) | `DINE_IN_RATIO=0` |
| 매장 주문 경로 검증 | `DINE_IN_RATIO=0.15` |
| 테이블 해제 지연이 해결된 뒤 | 비율 재검토 |

매장 주문을 켤 때 필요한 테이블 수는 아래로 계산한다.

```
필요 테이블 = 초당 매장 주문 수 × 해제까지 걸리는 시간(초) × 1.5
```

테이블이 부족하면 `503 DEPENDENCY_UNAVAILABLE`이 대량 발생한다. **409가 아니라 503이므로 서버 장애로 오인하기 쉽다.** 실패율에서 빼고 `table_blocked` 지표로 따로 센다.

### 3.3 데이터 초기화 절차

정리하지 않으면 회차가 반복될수록 데이터가 누적되어 응답시간이 자연히 증가하고, 개선 효과를 코드 변경 덕분인지 데이터 양 때문인지 구분할 수 없게 된다.

#### 3.3.1 정리 대상

이 시스템은 저장소가 3개다. 하나만 정리하면 상태가 어긋나 오히려 잘못된 결과가 나온다.

| 저장소 | 쌓이는 데이터 | 회차마다 정리 |
| --- | --- | :---: |
| PostgreSQL | 주문, 주문상품, 대기, 결제, 감사로그 | 선택 |
| MongoDB | 이벤트·상태 이력 | 선택 |
| **Redis** | **멱등키, 세션** | **필수** |

**Redis 멱등키는 반드시 지운다.** 시나리오 6은 같은 멱등키를 의도적으로 재사용한다. 이전 회차의 키가 남아 있으면 이번 회차의 최초 요청이 "이미 처리됨"으로 처리되어, 검증이 통과한 것처럼 보이지만 실제로는 아무것도 확인하지 못한다.

#### 3.3.2 기본 방식 — 회차별 전용 업체 (권장)

회차마다 새 테스트 업체를 만들고, 이전 회차 데이터는 지우지 않고 남겨둔다.

- 업체 코드에 실행 ID를 포함한다. 예: `LOADTEST-001`, `LOADTEST-002`
- 회차 간 데이터가 섞이지 않으므로 별도 삭제 없이 바로 다음 회차를 실행할 수 있다.
- 과거 회차 데이터가 남아 있어 사후 분석이 가능하다.

**누적 관리** — 5~10회차마다 오래된 `LOADTEST-*` 업체 데이터를 일괄 삭제한다. 방치하면 테이블이 커져 응답시간에 영향을 준다.

#### 3.3.3 회차 실행 절차

```
1. RUN_ID 확정                     예: LOADTEST-007
2. 초기 데이터 생성                 업체 → 매장 → 직원 계정 → 카테고리 → 상품 → 테이블
3. Redis에서 해당 RUN_ID 키 삭제     멱등키, 세션
4. k6 실행
5. 결과 저장 (데이터는 보존)
```

3단계는 `FLUSHALL`을 쓰지 않는다. 다른 작업의 데이터까지 삭제된다. 멱등키 형식이 `{RUN_ID}-...`(규칙 5)이므로 해당 접두사만 골라 삭제한다.

```bash
# 예시 — 패턴 매칭 삭제 (SCAN 기반, KEYS 사용 금지)
redis-cli --scan --pattern "idem:LOADTEST-007-*" | xargs -r redis-cli DEL
```

#### 3.3.4 초기 데이터 생성 방식

**API 호출 방식을 사용한다.** 실제 등록 흐름을 그대로 타므로 애플리케이션이 기대하는 상태와 어긋나지 않는다. DB에 직접 INSERT 하면 파생 필드나 이벤트 발행이 누락되어, 부하 테스트 중 원인 불명의 오류로 이어진다.

생성 순서와 수량은 아래를 기준으로 한다.

| 대상 | 수량 | 근거 |
| --- | ---: | --- |
| 업체 | 1 | 회차당 1개 |
| 매장 | 1 | |
| 직원 계정 | 최대 VU 수 이상 | 세션 배분용 (규칙 2) |
| 카테고리 | 3~5 | |
| 판매 상품 | 20~30 | 메뉴 조회 응답 크기를 현실적으로 유지 |
| 활성 테이블 | 매장 주문을 켤 때만 필요 | 규칙 8의 식으로 계산 |

생성 스크립트는 k6 `setup()`과 분리해 별도 실행한다. `setup()` 안에서 만들면 매 실행마다 데이터가 중복 생성된다.

#### 3.3.5 보조 방식

**영업일 분리** — 업체는 그대로 두고 `businessDate`만 회차마다 변경한다. 준비가 거의 필요 없어 스크립트 디버깅 단계에 적합하다. 단 데이터가 한 업체에 계속 쌓이고, Redis 정리는 여전히 필요하다. 정식 측정에는 사용하지 않는다.

**스냅샷 복원** — 테스트 직전 상태를 스냅샷으로 저장하고 회차 종료 후 복원한다. 가장 정확하지만 PostgreSQL·MongoDB·Redis를 **동일 시점으로 함께** 복원해야 하며, 하나라도 어긋나면 정합성이 깨진다. 개선 전후 성능을 정밀 비교하는 최종 측정 1회에만 사용한다.

#### 3.3.6 삭제 수단 확보

현재 API 명세에는 **업체 삭제가 없다.** 상태 변경(`PATCH /api/v1/provider/tenants/{tenantId}/status`)으로 비활성화만 가능하다.

따라서 누적 데이터 삭제는 DB 직접 실행이 필요하다. **부하 테스트 시작 전에 삭제 SQL을 미리 작성하고 검증해 둔다.** 데이터가 쌓인 뒤 급하게 작성하면 삭제 범위를 잘못 지정할 위험이 크다.

- 삭제 SQL은 `RUN_ID` 또는 테스트 업체 코드로만 범위를 한정한다.
- 실행 전 반드시 `SELECT`로 대상 건수를 먼저 확인한다.
- 외래 키 참조 순서(주문상품 → 주문 → 매장 → 업체)를 지킨다.

#### 3.3.7 실행 전 확정 사항

아래가 정해지지 않으면 부하 테스트를 시작하지 않는다.

| 항목 | 담당 | 확정 여부 |
| --- | --- | :---: |
| 초기 데이터 생성 스크립트 | `____` | ☐ |
| Redis 키 삭제 명령 | `____` | ☐ |
| 누적 데이터 삭제 SQL | `____` | ☐ |
| 삭제 주기 (예: 5회차마다) | `____` | ☐ |

## 4. 기준 부하 정의

시나리오 7·8의 "100%"는 아래 값을 가리킨다. **실행 전 팀에서 확정한다.**

| 항목 | 값 | 비고 |
| --- | --- | ---: |
| 기준 피크 처리량 (100%) | **`____` RPS** | 미정 시 20 RPS로 시작 |
| 기준 피크 동시 사용자 | **`____` VU** | 미정 시 30 VU로 시작 |

산정 근거: (예) 매장 1곳 피크 시간 주문 `__`건/분 × 목표 매장 수 × 요청 배수

기준값이 정해지지 않은 상태에서는 시나리오 1~6까지만 실행하고, 7~9는 확정 후 실행한다.

## 5. 측정 항목과 합격 기준

### 5.1 측정 항목

- 전체 및 태그별 요청 수, RPS
- 성공률·실패율 (의도된 오류 제외)
- 태그별 응답시간 평균, p90, p95, p99, 최대값
- HTTP 상태 코드별 발생 건수
- 타임아웃 및 연결 실패 건수
- 중복 생성 건수 (주문·대기)
- 재로그인 발생 횟수
- 서버 CPU, 메모리, Pod 재시작, DB 연결 수, Queue 적체량

### 5.2 합격 기준 (제안값)

운영 목표가 확정되기 전까지는 **제안값**으로만 사용한다.

```js
thresholds: {
  'http_req_failed':                          ['rate<0.01'],
  'http_req_duration{name:menu}':             ['p(95)<500'],
  'http_req_duration{name:order_list}':       ['p(95)<500'],
  'http_req_duration{name:order_detail}':     ['p(95)<500'],
  'http_req_duration{name:fulfillment_list}': ['p(95)<500'],
  'http_req_duration{name:order_create}':     ['p(95)<1000', 'p(99)<2000'],
  'http_req_duration{name:entry_create}':     ['p(95)<1000', 'p(99)<2000'],
  'checks':                                   ['rate>0.99'],
}
```

- 서버 오류(5xx): 0.1% 미만
- 테스트 중 비정상 Pod 재시작: 0회

## 6. 시나리오

### 시나리오 1. POS 로그인 및 기본 화면 조회

**목적** 영업 시작·교대 시간에 여러 직원이 동시에 로그인하고 주문 화면을 조회하는 상황을 검증한다.

**부하 모델** 닫힌 모델 (`ramping-vus`)

**사용자 흐름**

1. 업체 코드, 로그인 아이디, 비밀번호로 로그인한다. *(이 시나리오만 반복 로그인)*
2. 판매 메뉴를 조회한다.
3. 오늘 주문 목록을 조회한다.
4. 활성 테이블 목록을 조회한다.
5. 조리 목록을 조회한다.
6. 3~8초 대기 후 주문 목록과 조리 목록을 다시 조회한다.

**주요 API** `login` · `menu` · `order_list` · `table_list` · `fulfillment_list`

**부하 모델 제안**

| 단계 | VU | 지속 |
| --- | ---: | ---: |
| 1 | 10 | 3분 |
| 2 | 30 | 3분 |

**검증 항목**

- 로그인 성공 후 인증 세션이 정상 유지되는지
- 다른 업체 또는 다른 직원의 데이터가 섞이지 않는지
- 반복 조회 시 401·403·5xx가 비정상적으로 증가하지 않는지
- 로그인 부하가 조회 응답시간에 미치는 영향

---

### 시나리오 2. POS 주문 생성

> 기존 시나리오 2·3을 통합했다. 두 흐름의 차이는 `tableId` 유무뿐이므로 하나의 스크립트에서 비율로 섞는다.

**목적** 피크 시간에 직원이 주문을 연속 등록하는 상황을 검증한다.

**부하 모델** 열린 모델 (`ramping-arrival-rate`)

**사용자 흐름**

1. `setup()`에서 확보한 직원 세션을 사용한다.
2. 판매 메뉴를 조회한다. (반복당 1회, 캐시 가능)
3. 판매 중인 상품 1~4개를 무작위로 선택한다.
4. 유형을 결정한다. **기본은 `TAKEOUT` 100%** (규칙 8).
   - 매장 주문을 검증할 때만 `DINE_IN_RATIO`를 켠다.
5. 주문을 생성한다. (고유 `Idempotency-Key`)
6. 생성된 주문 상세를 조회한다.
7. 20% 확률로 주문 목록을 조회한다.

**주요 API** `menu` · `table_list` · `order_create` · `order_detail` · `order_list`

**부하 모델 제안**

| 단계 | 주문 생성률 | 지속 |
| --- | ---: | ---: |
| 정상 | 2 RPS | 5분 |
| 피크 | 8 RPS | 5분 |

**검증 항목**

- `TAKEOUT`에 `tableId`가 포함되지 않고, `DINE_IN`에 활성 `tableId`가 포함되는지
- 응답된 주문 번호와 합계 금액이 요청 상품과 일치하는지
- 주문 1건당 저장 데이터가 1건만 생성되는지
- 생성 직후 상세·목록 조회에서 즉시 확인되는지 (읽기 지연 여부)
- 비활성 테이블 사용 시 계약에 맞는 오류를 반환하는지 *(의도된 오류, 별도 집계)*

---

### 시나리오 3. 키오스크 주문 생성

> 기존 시나리오 4·5를 통합했다.

**목적** 여러 키오스크에서 고객이 동시에 메뉴를 조회하고 주문하는 상황과, POS 인증과의 분리를 검증한다.

**부하 모델** 닫힌 모델 (`ramping-vus`) — 키오스크는 대수가 물리적으로 고정되므로 닫힌 모델이 실제에 가깝다.

**사용자 흐름**

1. `setup()`에서 기기를 활성화한다. **활성화는 실행당 1회.**
2. 메뉴를 조회한다.
3. 상품 1~4개를 무작위로 선택한다.
4. 유형을 결정한다. **기본은 `TAKEOUT` 100%** (규칙 8).
5. 주문을 생성한다.
6. 주문 상태를 3~5초 간격으로 조회한다. 완료 또는 90초 도달 시 종료한다.
7. 30~90초 대기 후 반복한다.

**주요 API** `kiosk_activate` · `menu` · `table_list` · `order_create` · `order_detail`

**키오스크 제약 (구현 확인)**

- 주문 목록 조회·완료·취소는 키오스크 인증으로 호출할 수 없다 (`403 ACCESS_DENIED`). 시나리오에 포함하지 않는다.
- 주문 상세 조회는 주문 생성 응답의 `orderAccessToken`을 `X-Order-Access-Token` 헤더로 보내야 한다.

**부하 모델 제안**

| 단계 | 키오스크 수(VU) | 지속 |
| --- | ---: | ---: |
| 1 | 10 | 5분 |
| 2 | 30 | 5분 |

**검증 항목**

- POS 세션과 키오스크 인증이 서로 섞이지 않는지
- 상태 조회(폴링) 증가로 주문 생성 성능이 저하되지 않는지
- 인증 만료 시 다른 사용자 데이터가 노출되지 않는지
- 활성 테이블만 주문에 사용되는지

---

### 시나리오 4. 입장 대기 등록 및 상태 변경

**목적** 혼잡 시간에 대기 등록과 직원의 상태 변경이 동시에 발생하는 상황을 검증한다.

**부하 모델** 열린 모델 (등록·전이) + 닫힌 모델 (목록 조회) 병행

**사용자 흐름**

1. 새로운 입장 대기를 등록한다.
2. 해당 영업일의 대기 목록을 조회한다.
3. **자신이 등록한** 대기를 `입장`·`취소`·`미방문` 중 하나로 변경한다. *(규칙 3)*
4. 목록을 다시 조회해 반영 결과를 확인한다.

**주요 API** `entry_create` · `entry_list` · `entry_transition`

**부하 모델 제안**

| 항목 | 값 | 지속 |
| --- | ---: | ---: |
| 대기 등록 | 3 RPS | 8분 |
| 목록 조회 | 15 VU, 3~5초 간격 | 8분 |
| 상태 변경 | 2 RPS | 8분 |

**검증 항목**

- 대기 번호가 중복되지 않는지
- 이미 종료된 대기의 재처리가 거부되는지 *(의도된 오류, 별도 집계)*
- 목록 조회 결과와 상태 변경 결과가 일치하는지
- 대기 목록이 길어질수록 조회 응답시간이 어떻게 변하는지

---

### 시나리오 5. 조리 처리 및 주문 완료

> 주문 완료·취소 API를 추가했다. 기존 문서에서는 주문 생애주기의 마지막 단계가 누락되어 있었다.

**목적** 주문이 연속 생성될 때 조리 목록 반영, 준비 완료, 주문 완료·취소까지 전체 흐름이 안정적으로 처리되는지 확인한다.

> ⚠ **선행 확인 필요** — 조리 항목은 HTTP로 생성되지 않는다. `OrderAccepted` 이벤트를 소비할 때 `PREPARING` 상태로 자동 생성된다. 즉 **결제 승인 흐름이 선행되지 않으면 조리 목록이 계속 빌 수 있다.** 이 문서는 결제를 부하 대상에서 제외했으므로(9장), 아래 셋 중 하나를 팀에서 정해야 이 시나리오가 의미를 갖는다.
>
> 1. 결제를 Stub으로 두고 승인까지 태운다 (9장 수정)
> 2. 부하 테스트 환경에서만 주문을 자동 `ACCEPTED`로 넘기는 설정을 둔다
> 3. 조리 흐름 부하 테스트를 범위에서 제외한다
>
> 결정 전까지는 이 시나리오를 "주문 생성 → 완료·취소" 검증으로만 취급한다.

**부하 모델** 열린 모델 (주문 생성·전이) + 닫힌 모델 (조리 목록 조회)

**사용자 흐름**

1. POS와 키오스크 주문을 혼합 생성한다.
2. 조리 담당 VU가 조리 목록을 반복 조회한다.
3. **자신이 생성한** 주문 항목을 준비 완료로 변경한다.
4. 준비 완료된 주문의 **90%는 주문 완료**, **10%는 주문 취소** 처리한다.
5. 조리 목록과 주문 상세에서 최종 상태를 재확인한다.

**주요 API** `order_create` · `fulfillment_list` · `fulfillment_ready` · `order_complete` · `order_cancel` · `order_detail`

**부하 모델 제안**

| 항목 | 값 | 지속 |
| --- | ---: | ---: |
| 주문 생성 | 5 RPS | 10분 |
| 조리 목록 조회 | 10 VU, 2~4초 간격 | 10분 |
| 준비 완료 | 3 RPS | 10분 |
| 완료·취소 | 3 RPS | 10분 |

**검증 항목**

- 생성된 주문이 조리 목록에 누락 없이 반영되는지
- **주문 생성 → 조리 목록 반영까지의 지연 시간** (커스텀 Trend로 기록)
- 동일 항목의 중복 준비 완료가 데이터 중복을 만들지 않는지
- 주문 취소 시 테이블 상태·재고·연관 데이터가 일관되게 복구되는지
- 취소 처리가 완료 처리보다 현저히 느리지 않은지

---

### 시나리오 6. 멱등성 및 동시 요청

**목적** 네트워크 재시도나 버튼 중복 입력 상황에서도 주문과 대기 등록이 중복 생성되지 않는지 검증한다.

**부하 모델** 이 시나리오는 처리량이 아니라 **정확성**을 본다. 낮은 부하로 실행한다.

**검증 유형**

| # | 방법 | 기대 결과 |
| ---: | --- | --- |
| 1 | 같은 본문 + 같은 키를 **`http.batch()`로 동시에 5회** 전송 | 데이터 1건. 응답은 모두 동일한 결과 |
| 2 | 최초 성공 후 같은 키로 재전송 | 최초 결과 재사용. 데이터 증가 없음 |
| 3 | 같은 키에 다른 상품·수량 | 충돌 응답. 데이터 증가 없음 *(의도된 오류)* |
| 4 | 같은 내용을 서로 다른 키로 전송 | 각각 정상 처리. 데이터 2건 |

> 유형 1은 반드시 `http.batch()`를 쓴다. VU는 순차 실행이므로 반복문으로는 실제 동시 요청이 만들어지지 않는다.

**대상 API** `order_create` · `entry_create`

**부하 모델 제안** 10 VU, 5분. 각 VU가 유형 1~4를 순환한다.

**검증 항목**

- 각 유형의 기대 결과가 100% 만족되는지 (`checks` rate = 1.0)
- 타임아웃 후 재시도에도 중복이 생기지 않는지
- 멱등키 저장소가 부하 상황에서 정상 동작하는지

---

### 시나리오 7. 실제 영업 혼합 부하

**목적** 단일 API가 아니라 실제 영업 중 함께 발생하는 요청을 혼합해 전체 시스템 성능을 확인한다.

**부하 모델** 열린 모델 (`ramping-arrival-rate`)

**요청 비율**

| 업무 | 비율 |
| --- | ---: |
| 주문·조리·대기 목록 조회 | 45% |
| POS 주문 생성 | 20% |
| 키오스크 주문 생성 | 20% |
| 주문 상태 및 상세 조회 | 10% |
| 대기·조리 상태 변경 | 5% |

주문 생성분은 기본적으로 전부 포장이다 (규칙 8).

**부하 단계** (기준 부하 = 4장에서 정한 값)

| 단계 | 목표 | 지속 |
| --- | ---: | ---: |
| 준비 | 0% → 30% | 3분 |
| 정상 영업 | 30% 유지 | 7분 |
| 피크 진입 | 30% → 100% | 3분 |
| 피크 유지 | 100% 유지 | 10분 |
| 회복 확인 | 100% → 20% | 2분 |
| 종료 | 20% → 0% | 2분 |

총 27분.

**검증 항목**

- 피크 구간의 오류율과 p95·p99 응답시간
- 부하 감소 후 응답시간·자원 사용량이 정상 수준으로 회복되는지
- 주문 생성 후 조리 목록 반영까지의 지연
- 서비스별 CPU·메모리·DB 연결·Queue 적체 변화
- 특정 서비스 지연이 다른 API의 연쇄 지연으로 확대되는지

---

### 시나리오 8. 순간 급증 (Spike)

**목적** 짧은 시간에 요청이 급증하는 상황에서 방어와 회복 능력을 확인한다.

**부하 모델** 열린 모델. 요청 비율은 시나리오 7과 동일.

**부하 단계**

| 단계 | 목표 | 지속 |
| --- | ---: | ---: |
| 평상시 | 30% | 3분 |
| 급증 | 30% → 150% (30초 이내) | 30초 |
| 최대 유지 | 150% | 3분 |
| 감소 | 150% → 30% (1분 이내) | 1분 |
| 회복 관찰 | 30% | 5분 |

**검증 항목**

- 급증 구간에서 타임아웃·5xx가 허용 범위 내인지
- 주문 유실과 중복 생성이 없는지
- Queue·DB 연결 고갈 또는 Pod 재시작이 없는지
- **감소 후 몇 분 만에 정상 응답시간으로 돌아오는지** (회복 시간 기록)

---

### 시나리오 9. 장시간 안정성 (Soak)

> 기존 2~8시간 → **1시간**으로 축소했다. 메모리·연결 누수는 대부분 첫 1시간의 증가 기울기로 판별 가능하다. 기울기가 보이면 그때 장시간 재실행한다.

**목적** 반복 요청이 계속될 때 메모리 누수, 연결 누수, Queue 적체 등 장기 문제를 확인한다.

**부하 모델** 열린 모델. 기준 부하의 **40%**. 요청 비율은 시나리오 7과 동일.

**지속 시간** 1시간. *(1차에서 우상향 기울기가 관측되면 4시간으로 재실행)*

**검증 항목**

- 시간 경과에 따른 응답시간 증가 여부 — **10분 단위 p95를 비교해 기울기를 본다**
- 메모리·스레드·DB 연결 수의 지속 증가 여부
- Queue 적체와 이벤트 처리 지연
- 세션 만료·갱신 처리 (재로그인 카운터 확인)
- 누적 오류율과 비정상 재시작
- 실행 중 영업일(`businessDate`)이 바뀌는 경우 조회·집계가 정상 동작하는지

### 시나리오 10. 한계 탐색 (Stress)

**목적** 부하를 계단식으로 올려 **어느 지점에서 처음 무너지는지** 찾는다. 이 문서의 다른 시나리오는 "정해진 부하를 견디는가"를 보지만, 이 시나리오만은 **한계 자체를 찾는 것**이 목적이다.

**부하 모델** 닫힌 모델 (`ramping-vus`)을 계단식으로.

**부하 단계**

| 단계 | 동시 사용자 | 지속 |
| ---: | ---: | ---: |
| 1 | 100 | 3분 |
| 2 | 200 | 3분 |
| 3 | 300 | 3분 |
| 4 | 400 | 3분 |
| 5 | 500 | 3분 |

단계 사이에 20초를 비워 회복을 관찰한다. 요청 구성은 시나리오 7과 동일.

**단계별로 지표를 분리한다**

각 단계에 `step` 태그를 붙인다. 그래야 "어느 단계에서 튀었는지"를 볼 수 있다.

```
http_req_duration{step:100} … {step:500}
http_req_failed{step:100}   … {step:500}
```

**읽는 법**

| 관찰 | 뜻 |
| --- | --- |
| p95가 처음으로 눈에 띄게 튀는 단계 | 여기가 한계 |
| 실패율이 처음 오르는 단계 | 여기가 한계 |
| 마지막 단계까지 평탄 | **단계를 더 올려 다시 실행** |

마지막 단계까지 멀쩡하면 이 시나리오는 **실패한 것이다.** 한계를 못 찾았다는 뜻이므로 `600, 800, 1000`으로 올려 다시 돌린다.

**검증 항목**

- 처음으로 성능이 꺾이는 동시 사용자 수
- 그 지점에서 무엇이 먼저 한계에 도달했는지 (CPU / DB 연결 / Queue 적체 / 특정 API)
- 단계를 내렸을 때 정상으로 회복되는지
- 5xx가 나기 시작하는 지점과 그 직전 지점의 차이

**합격 기준**

없다. **"몇 명에서, 무엇 때문에 막혔다"**는 문장을 얻으면 성공이다.

"500명을 통과했다"보다 **"400명에서 DB 연결이 고갈됐다"**가 더 가치 있는 결과다.

## 8. 중단 기준

### 8.1 자동 중단 (k6 threshold)

무인 실행(특히 시나리오 9) 중 아래 조건이 걸리면 자동으로 중단한다.

```js
thresholds: {
  'http_req_failed': [
    { threshold: 'rate<0.05', abortOnFail: true, delayAbortEval: '1m' },
  ],
  'http_req_duration{name:order_create}': [
    { threshold: 'p(95)<5000', abortOnFail: true, delayAbortEval: '1m' },
  ],
}
```

### 8.2 수동 중단

관측 중 아래를 확인하면 즉시 중단하고 원인을 파악한다.

- 운영 환경 또는 실제 결제 키로 요청이 나간 경우 **(최우선)**
- 테스트 대상 외 업체·매장 데이터가 조회된 경우 **(데이터 격리 사고)**
- 주문·대기 데이터의 중복 또는 유실이 확인된 경우
- DB 연결 고갈, Queue 처리 중단, Pod 반복 재시작
- 응답시간이 지속 증가하며 부하 감소 후에도 회복되지 않는 경우

## 9. 결제 시나리오

결제는 외부 비용과 실제 승인 위험이 있으므로 **부하 테스트 대상에서 제외한다.** 단일 사용자 기능 확인까지만 수행한다.

**기능 확인 흐름** (1 VU, 각 1회)

1. 주문 생성
2. `POST /api/v1/payments` — 결제 생성
3. `POST /api/v1/payments/{id}/confirm` — 결제 승인
4. `GET /api/v1/payments/{id}` — 결과 조회
5. `POST /api/v1/payments/{id}/cancel` — 취소 및 최종 상태 확인

- 생성·승인·취소는 각각 **서로 다른** `Idempotency-Key`를 사용한다.
- Stub 또는 Toss Sandbox 전용 키만 사용한다. 운영 키 사용 시 즉시 중단(8.2).
- 결제에 부하를 걸어야 할 필요가 생기면 별도 문서로 계획을 세우고 팀 승인 후 진행한다.

## 10. 결과 보고 항목

각 실행 결과에 다음을 기록한다.

**실행 정보**

- 실행 일시, 대상 환경, `RUN_ID`
- 배포 버전 및 이미지 SHA
- 테스트 업체·매장, 사전 데이터 규모 (상품 수, 테이블 수, 기존 주문 수)
- 실행 시나리오와 부하 단계, 기준 부하 값

**성능 결과**

- 총 요청 수, RPS, 성공률, 실패율
- **태그별** p90·p95·p99 응답시간
- 주요 오류 코드와 발생 횟수 (의도된 오류와 분리)
- 재로그인 발생 횟수

**정합성 결과**

- 주문·대기의 중복 또는 유실 여부
- 주문 생성 → 조리 목록 반영 지연 (평균, p95)

**자원 및 결론**

- 서비스·DB·Queue 자원 사용량
- 최초 병목 지점과 원인 추정
- 재현 방법과 개선 후 재시험 결과

## 11. 스크립트 구현 시 확인된 사항

명세와 구현을 대조하며 스크립트를 작성한 결과, 문서 작성 시점에 알지 못했던 제약이 나왔다. 위 본문에 이미 반영했고, 여기에 한 번에 모아둔다.

| # | 확인된 사항 | 영향 |
| ---: | --- | --- |
| 1 | 조리 항목은 `OrderAccepted` 이벤트로 생성됨 | 시나리오 5 — **팀 결정 필요** |
| 2 | 직원 세션과 키오스크 인증을 한 VU에서 섞으면 `401` | 규칙 2, 시나리오 7~9는 executor 분리 |
| 3 | 키오스크는 주문 목록·완료·취소 불가 (`403`) | 시나리오 3 범위 축소 |
| 4 | 키오스크 주문 상세는 `X-Order-Access-Token` 필요 | 시나리오 3 |
| 5 | 비활성 테이블 위반은 `400` (409·422 아님) | 규칙 4 |
| 6 | 멱등 충돌 `code`가 문서와 구현이 다름 | 규칙 4 — HTTP 409로만 판정 |
| 7 | `GET /api/v1/tables`는 ACTIVE만 반환 | 아래 참고 |
| 8 | 주문 요청에 금액·옵션 필드 없음 (`productId`, `quantity`만) | 스크립트 |
| 9 | 업체·최초 OWNER 생성은 Provider Admin (OIDC, admin 프로파일) | 3.3.4 — 자동화 불가, 수동 선행 |
| 10 | 키오스크 기기 **등록** API를 확인하지 못함 | 시나리오 3 실행 전 확인 필요 |
| 11 | **테이블 1개 = 동시 주문 1건** (DB 유니크 인덱스로 강제) | 규칙 8 — 매장 주문 기본 제외 |
| 12 | **테이블 해제가 최대 30초 지연** | 아래 참고 — **제품 확인 필요** |

**7번 보충** — `GET /api/v1/tables`가 `ACTIVE`만 돌려주므로, "비활성 테이블로 주문하면 거절되는지" 검증은 비활성 테이블 id를 미리 확보하지 않으면 실행할 수 없다. 시드 단계에서 테이블 하나를 만든 뒤 비활성화하고 그 id를 스크립트에 넘기는 절차가 추가로 필요하다. 현재 스크립트에는 포함되어 있지 않다.

**10번 보충** — `POST /api/v1/kiosk-auth/activate`는 이미 등록된 기기를 활성화하는 API다. 기기 자체를 등록하는 경로를 확인하지 못했다. 시나리오 3과 혼합 부하의 키오스크 부분을 실행하려면 테스트 기기를 미리 등록해 두어야 한다.

**11·12번 보충 — 테이블 처리량 상한**

매장 주문은 테이블에 예약을 걸고, 그 예약은 DB 부분 유니크 인덱스로 **테이블당 1건**만 허용된다. 같은 테이블 요청은 `SELECT ... FOR UPDATE`로 직렬화되며, 이미 예약된 테이블에 주문하면 store-access는 409를 반환하지만 **외부 응답은 503**으로 바뀐다.

해제는 즉시 일어나지 않는다. 주문 완료·취소 시 `table_reservation_release_task`에 작업만 적재하고, 실제 해제는 `doro.commerce.table-reservation.release-retry-delay`(기본 **30초**) 주기의 스케줄러가 수행한다. 동기 해제 시도는 코드에 없다. 따라서 완료 직후 같은 테이블로 주문하면 평균 15초, 최대 30초 막힌다.

이 설계 자체(작업 적재 후 재시도)는 "테이블이 영구히 잠기는" 최악을 막는 올바른 방향이다. 다만 설정값 이름이 **재시도 간격**인데 첫 시도까지 이 주기를 기다린다는 점이 문제다.

**팀 확인 사항**

1. 30초 지연이 의도된 것인가?
2. 실제 매장에서 손님 교대 시 이 지연이 문제되지 않는가?

개선안은 둘 중 하나다.

- 주기를 짧게 (`PT30S` → `PT2S`) — 설정값만 변경
- 완료·취소 시점에 해제를 **한 번 동기 시도**하고, 실패 시에만 스케줄러에 위임 — 코드 변경

**확인 방법** — 개발 환경에서 `매장 주문 → 완료 → 같은 테이블로 재주문`을 즉시 해보면 1분 안에 판별된다.

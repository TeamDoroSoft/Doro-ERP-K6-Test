## 1. 무엇을 테스트하는가

부하 테스트의 목적은 "몇 명까지 버티는지 증명"이 아니라 **"어디서 무엇 때문에 먼저 무너지는지 찾는 것"** 이다.

시나리오는 성격에 따라 4종류로 구성했다.

| 종류 | 시나리오 | 목적 |
| --- | --- | --- |
| 부하 | 1~5, 7 | 예상 부하에서 정상 동작하는가 |
| 정합성 | 6 | 버튼 연타·재시도에도 중복이 안 생기는가 |
| **한계 탐색** | **10** | **어디서 처음 무너지는가** ⭐ |
| 회복력·안정성 | 8, 9 | 급증 후 회복하는가 / 오래 켜둬도 되는가 |

### 시나리오 목록

| # | 내용 | 부하 방식 |
| ---: | --- | --- |
| 1 | POS 로그인·기본 화면 조회 | 동시 사용자 10 → 30 |
| 2 | POS 주문 생성 | 초당 요청 고정 |
| 3 | 키오스크 주문 생성 | 동시 기기 10 → 30 |
| 4 | 입장 대기 등록·상태 변경 | 등록/조회 병행 |
| 5 | 조리 처리 및 주문 완료·취소 | 주문 투입 + 주방 조회 |
| 6 | 멱등성·동시 요청 | 저부하, 정확성 검증 |
| 7 | 실제 영업 혼합 부하 | 27분, 조회 45% / 주문 40% / 기타 15% |
| 8 | 순간 급증 (Spike) | 30초 만에 150% |
| 9 | 장시간 안정성 (Soak) | 1시간 |
| **10** | **한계 탐색 (Stress)** | **100 → 200 → 300 → 400 → 500 계단식** |

### 부하 기준값

| 단계 | 동시 사용자 |
| --- | ---: |
| 정상 | 100 |
| 피크 | 300 |
| 한계 확인 | 500 |

팀 협의 목표치이며 실측 후 조정한다. 시나리오 10에서 500까지 이상이 없으면 **한계를 못 찾은 것**이므로 단계를 올려 재실행한다.

### 범위에서 제외한 것

- **실제 결제 승인** — 외부 비용과 승인 위험. 단일 사용자 기능 확인까지만 수행
- **매장 주문(DINE_IN)** — 아래 이슈 1번 참조. 기본값은 포장 100%
- **운영 환경** — 전용 테스트 환경에서만 실행

## 2. 발견한 문제

### ⚠ 이슈 1. 테이블 해제가 최대 30초 지연된다 — **제품 이슈**

**증상**

손님이 나가고 직원이 "주문 완료"를 눌러도, **같은 테이블에 다음 주문이 즉시 들어가지 않는다.** 평균 15초, 최대 30초 막힌다. 그동안 반환되는 코드는 `503 SERVICE_UNAVAILABLE` 이라 직원에게는 시스템 장애로 보인다.

**원인**

`OrderService.complete()` / `cancel()` 는 해제 작업을 `table_reservation_release_task` 에 적재만 하고, 실제 해제는 스케줄러가 수행한다. **동기 해제 시도는 코드에 없다.**

```java
// TableReservationReleaseRecovery.java:33
@Scheduled(fixedDelayString = "${doro.commerce.table-reservation.release-retry-delay:PT30S}")
void releaseDueReservations() { ... }
```

**주목할 점** — 같은 프로젝트의 다른 스케줄러는 모두 1초다.

| 스케줄러 | 주기 |
| --- | ---: |
| `AuditOutboxScheduler` | PT1S |
| `QueueOrderOutboxPublisher` | PT1S |
| **`TableReservationReleaseRecovery`** | **PT30S** |

설정 키 이름이 `release-**retry**-delay`(재시도 간격)인데 **첫 시도까지 이 주기를 기다린다.** 재시도용 값이 평상시 지연으로 쓰이고 있는 것으로 보인다.

**영향**

- 실제 매장: 피크 시간 손님 교대 시 주문 지연 (테이블 개수와 무관하게 발생)
- 부하 테스트: 매장 주문 처리량이 `테이블 수 ÷ 35초` 로 상한이 걸림 (테이블 500개 기준 초당 14건)

**개선안**

| 방법 | 변경 범위 | 비고 |
| --- | --- | --- |
| A. 주기를 1~2초로 | 설정값 1줄 | 다른 스케줄러와 동일하게 맞춤 |
| B. 완료 시점에 동기 해제 1회 시도, 실패 시 스케줄러 위임 | 코드 변경 | 정석. 안전장치 유지하며 평상시 즉시 |

**확인 방법** — 개발 환경에서 `매장 주문 → 완료 → 같은 테이블 재주문` 을 즉시 시도. 1분이면 판별된다.

**2026-08-27 재확인 — 변동 없음.** `PT30S` 그대로이며, `application.yaml`·GitOps 매니페스트 어디에도 이 키를 덮어쓰는 설정이 없다. 즉 A안(설정값 변경)은 **yaml 한 줄 추가**로 끝난다. 코드 변경이 필요 없다.

추가로 발견 — 실패 시 재시도 간격도 `plusSeconds(30)`으로 하드코딩되어 있다. 최초 30초 + 재시도마다 30초가 누적되므로, Store Access가 불안정하면 60초 이상도 가능하다.

> **결정 필요** — 의도한 동작인가? 아니라면 A / B 중 어느 쪽인가?

### ⚠ 이슈 2. 조리 목록이 결제 없이는 채워지지 않는다 — **테스트 범위 결정 필요**

**증상**

시나리오 5(조리 처리)를 실행해도 조리 목록이 비어 있을 수 있다.

**원인**

조리 항목은 HTTP API로 생성되지 않는다. `OrderAccepted` 이벤트를 소비할 때 `PREPARING` 상태로 자동 생성된다. 즉 **결제 승인이 선행되어야 한다.**

본 문서는 결제를 부하 대상에서 제외했으므로, 현재 구성으로는 조리 흐름이 검증되지 않는다.

**선택지**

| 안 | 내용 | 비용 |
| --- | --- | --- |
| A | 결제를 Stub으로 두고 승인까지 태운다 | 문서·스크립트 수정 |
| B | 테스트 환경에서만 주문을 자동 `ACCEPTED` 로 전이 | 서비스 설정 추가 |
| C | 조리 흐름 부하 테스트를 범위에서 제외 | 없음 (커버리지 감소) |

현재 스크립트는 조리 목록이 비면 `fulfillment_empty` 지표를 올리고, **주문 생성 → 완료·취소** 까지만 검증한다.

**2026-08-27 재확인 — 변동 없음.** `payment-api`에 Stub 어댑터가 추가되지 않았고, 결제 없이 `ACCEPTED`로 전이되는 우회 경로도 없다.

A안을 택할 경우의 구현 지점은 확인해 두었다. `PaymentConfiguration.paymentProvider()`가 유일한 교체 지점이며, `PaymentProviderPort`를 구현한 Stub을 조건부로 주입하면 된다. Stub은 요청의 `providerOrderId`·`amount`를 그대로 되돌려주고 통화를 `KRW`로 반환해야 한다. 하나라도 어긋나면 `PAID`가 아니라 `REVIEW_REQUIRED`로 빠진다.

운영 환경에는 이미 `PAYMENT_OUTBOX_ENABLED=true`, `PAYMENT_COMMERCE_ELIGIBILITY_ENABLED=true`가 적용되어 있으므로, 결제만 성립하면 `주문 → ACCEPTED → 조리 항목` 사슬은 이어진다.

> **결정 필요** — A / B / C 중 어느 쪽인가?

### ✅ 이슈 3. 키오스크 기기 등록 경로 — **해소**

~~기기 자체를 등록하는 경로를 확인하지 못했다.~~

등록 API는 처음부터 존재했다. 8/25 조사에서 놓친 것이다.

```
POST /api/v1/kiosk-devices        { "deviceCode": "device001" }
→ 200 { "kioskDeviceId": UUID, "credential": "kdc_xxx.yyy" }
```

`kiosk-auth/activate`는 그 다음 단계로, 여기서 받은 `credential`을 사용한다.

**실행 시 제약 3가지**

| 항목 | 내용 |
| --- | --- |
| 재인증 | 로그인 후 **15분 이내**. `POST /api/v1/auth/reauthenticate`로 갱신 |
| 멱등성 없음 | 재실행 시 중복 등록 시도 → `(업체, 매장, deviceCode)` 유니크 제약으로 실패 |
| `credential` 1회성 | 등록 응답에만 나온다. 시드 산출물에 저장 필수 |

추가로 **목록 조회 API가 신설되었다**(2026-08-26, Service PR #73).

```
GET /api/v1/kiosk-devices   → 재인증 불필요
```

시드 실행 후 기기가 실제로 몇 개 등록됐는지 확인할 수 있다. 프론트 관리 화면도 같은 날 완성되었다(Front PR #29).

> **남은 작업** — `seed/seed.js`에 `login → reauthenticate → 기기 N개 등록 → credential 저장` 절차 추가. 팀 결정과 무관하게 지금 진행 가능.

### ✅ 이슈 4. 업체·최초 계정 생성 자동화 불가 — **수동으로 확정**

업체 생성(`POST /api/v1/provider/tenants`)과 최초 OWNER 생성은 Provider Admin 경로다. `admin` 프로파일 Edge에서만 노출되고 OIDC 로그인이 필요해 스크립트로 자동화하기 어렵다.

**8/25 이후 확인** — 이것은 임시 상태가 아니라 **의도된 설계**다. Service PR #67에서 `@Profile("!admin")` 기반의 `PublicEdgeRuntime` 경계가 도입되었고, 주석에 다음과 같이 명시되어 있다.

> The Provider Admin runtime intentionally has no access to public Edge upstream URLs or HMAC credentials.

우회로가 설계상 차단되어 있으므로 **"업체·OWNER 1건은 수동 생성"을 정식 절차로 확정한다.** 추가 조사는 불필요하다.

**수동 절차** (약 5분, 1회)

```
1. SSM 포트 포워딩으로 터널 (관리 EC2 경유, 로컬 8443)
2. hosts에 admin.doro.minseok.click → 127.0.0.1 등록
3. https://admin.doro.minseok.click:8443 접속 → OIDC 로그인
4. 업체 관리 → 신규 업체 등록 (업체 코드 / 업체명 / 첫 매장명 / 시간대)
```

이후 카테고리·상품·테이블·직원·키오스크 기기는 시드 스크립트가 생성한다.

초기 데이터 생성 스크립트는 **업체와 OWNER가 이미 존재한다고 가정**하고 그 아래(카테고리·상품·테이블·직원)만 생성한다. 업체 1건은 수동 생성으로 대응 가능하다.

## 3. 그 외 확인된 구현 사항

문서에 반영 완료. 별도 조치는 불필요하다.

| 항목 | 내용 |
| --- | --- |
| 인증 분리 | 직원 세션과 키오스크 인증을 한 사용자에 혼용하면 `401`. 혼합 부하에서 분리 처리 |
| 키오스크 권한 | 주문 목록·완료·취소 불가(`403`). 상세 조회는 `X-Order-Access-Token` 필요 |
| 오류 코드 차이 | 비활성 테이블 → `400`(문서 예상 409/422와 상이). 멱등 충돌 코드 문자열이 계약 문서와 구현이 다름 |
| 테이블 조회 | `GET /api/v1/tables` 는 ACTIVE만 반환. 비활성 테이블 검증은 사전 준비 필요 |
| 주문 요청 필드 | `productId` + `quantity` 만 전송. 금액·옵션 필드 없음 |

## 4. 테스트 신뢰성을 위해 정한 규칙

결과를 읽을 수 없게 만드는 흔한 함정을 방지하기 위해 스크립트 작성 규칙 8개를 문서화했다. 주요 항목은 다음과 같다.

- **요청별 고정 태그** — URL에 id가 들어가면 지표가 주문 건마다 분산되어 p95 산출 불가
- **인증 재사용** — 매 요청 로그인 시 비밀번호 해싱이 CPU를 점유해 주문 성능이 아닌 인증 성능을 측정하게 됨
- **데이터 소유권 분리** — 여러 사용자가 같은 항목을 변경하면 충돌이 실패로 집계됨
- **의도된 오류 분리** — 거절되는 것이 정상인 요청(400/409/503)을 실패율에서 제외
- **회차별 데이터 초기화** — 특히 Redis 멱등키. 미삭제 시 멱등성 검증이 무의미해짐

상세는 시나리오 문서 3.2 참조.

## 6. 실행 방법

```bash
export BASE_URL=<테스트 환경 Edge 주소>
export RUN_ID=LOADTEST-001

./run.sh seed      # 초기 데이터 생성
./run.sh smoke     # 스크립트 점검
./run.sh basic     # 시나리오 1~6
./run.sh stress    # 한계 탐색
./run.sh full      # 전체
```

상세는 저장소 `README.md`, 시나리오 정의는 `docs/Doro-ERP-k6-부하테스트-시나리오.md` 참조.

**실행 환경 원칙** (시나리오 문서 3.4 신설)

- 부하 테스트는 **배포 환경에서만** 실행한다. 로컬 실행 결과는 스크립트 검증 용도로만 쓰고 성능 수치로 인용하지 않는다
- 부하 생성기는 **같은 VPC 안의 별도 EC2**에서 실행한다. 개인 노트북에서 쏘면 회선 지연이 측정값에 섞인다
- 노드(`t3.large`)와 Redis(`cache.t4g.micro`)는 버스터블이다. **시나리오 9(Soak) 중 CPU 크레딧 소진으로 p95가 튀는 구간**이 나올 수 있으므로 `CPUCreditBalance`를 함께 기록한다
- Infra에 CloudWatch 운영 대시보드가 추가되었다(2026-08-26). 실행 중 함께 캡처하면 병목 판정 근거가 된다

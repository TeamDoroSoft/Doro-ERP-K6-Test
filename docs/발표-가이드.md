# 부하 테스트 발표 가이드

무엇을 보여주고, 어떻게 말할 것인가

---

## 0. 먼저 정할 것 — 발표의 한 문장

발표가 끝났을 때 청중 머릿속에 남아야 할 문장을 먼저 정한다. 슬라이드는 그 문장을 뒷받침하는 도구다.

**나쁜 한 문장**

> "동시 사용자 500명을 통과했습니다."

숫자만 있고 의미가 없다. *"그래서요?"* 로 이어지고, *"501명이면요?"* 에 답을 못 한다.

**좋은 한 문장**

> "포장 주문 기준 초당 40건까지 처리했고, 그 다음 병목은 테이블 예약이며 원인과 개선안까지 확인했습니다."

**한계 → 원인 → 개선안**이 한 줄에 들어간다. 더 물어볼 게 없다.

부하 테스트 발표에서 평가받는 것은 **통과 여부가 아니라 "시스템을 얼마나 이해하고 있는가"** 다. 어디가 약한지 모르는 팀보다, 알고 설명할 수 있는 팀이 낫다.

---

## 1. 발표 흐름 (8장 구성)

| # | 슬라이드 | 시간 | 핵심 |
| ---: | --- | ---: | --- |
| 1 | 왜 했는가 | 30초 | 목적은 "증명"이 아니라 "한계 찾기" |
| 2 | 어떻게 설계했는가 | 1분 | 시나리오 종류와 부하 모델 |
| 3 | 결과를 믿을 수 있는 이유 | 1분 | ★ 차별화 지점 |
| 4 | 결과 ① 정상 부하 | 30초 | 빠르게 넘어감 |
| 5 | **결과 ② 한계 지점** | **2분** | **★ 하이라이트** |
| 6 | **발견한 문제** | **2분** | **★ 하이라이트** |
| 7 | 개선 후 재측정 | 1분 | 있으면 최고, 없으면 생략 |
| 8 | 정리 | 30초 | 한 문장 반복 |

총 8~9분. 5·6번에 시간을 몰아준다.

---

## 2. 슬라이드별 내용

### 1장. 왜 했는가

**말할 것**

> "기능이 되는 것과 몰릴 때 되는 것은 다릅니다. 개발자 한 명이 클릭하면 다 되지만, 점심 피크에 열 명이 동시에 누르면 이야기가 달라집니다.
> 그래서 목표를 '몇 명까지 버티는지 증명'이 아니라 **'어디서 무엇 때문에 먼저 무너지는지 찾기'** 로 잡았습니다."

**보여줄 것** — 텍스트만. 그래프 필요 없다.

30초 안에 끝낸다. 여기서 시간을 쓰면 뒤가 밀린다.

---

### 2장. 어떻게 설계했는가

**말할 것**

> "매장에서 실제로 일어나는 흐름을 시나리오로 옮겼습니다. POS 주문, 키오스크 주문, 웨이팅, 주방 처리를 각각 만들고, 마지막에 전부 섞었습니다.
> 부하를 주는 방식도 두 가지로 나눴습니다. **사용자 수를 고정하는 방식**과 **초당 요청 수를 고정하는 방식**인데, 실제 피크는 후자에 가깝습니다. 서버가 느려져도 손님은 계속 오니까요."

**보여줄 것**

시나리오 표 (10개 전부 나열하지 말고 4종류로 묶어서)

| 종류 | 목적 |
| --- | --- |
| 부하 | 예상 부하에서 정상 동작하는가 |
| 정합성 | 버튼 연타에도 중복이 안 생기는가 |
| **한계 탐색** | **어디서 처음 무너지는가** |
| 회복력·안정성 | 급증 후 회복 / 오래 켜둬도 되는가 |

---

### 3장. 결과를 믿을 수 있는 이유 ★

**여기가 다른 팀과 갈리는 지점이다.** 부하 테스트는 잘못 짜면 결과가 무의미해지는데, 그걸 알고 대비했다는 걸 보여준다.

**말할 것** — 3개만 고른다. 전부 말하면 지루하다.

> "부하 테스트는 잘못 짜면 결과를 못 읽습니다. 세 가지를 특히 조심했습니다.
>
> 첫째, **주문 조회 API는 주문번호마다 주소가 다릅니다.** 그냥 두면 통계가 9천 개로 쪼개져서 평균을 낼 수 없습니다. 그래서 모든 요청에 고정 이름표를 붙였습니다.
>
> 둘째, **매 요청마다 로그인하면 안 됩니다.** 비밀번호 검증은 의도적으로 느린 연산이라, 주문 성능이 아니라 로그인 성능을 재게 됩니다.
>
> 셋째, **일부러 실패시키는 요청이 있습니다.** '같은 키로 두 번 보내면 거절되는가' 같은 건 거절이 정상인데, 그냥 두면 실패율에 섞입니다. 분리해서 집계했습니다."

**보여줄 것** — 3줄짜리 표. 각 줄에 "문제 → 대응".

**왜 넣는가** — 심사위원이 부하 테스트를 아는 사람이면 여기서 신뢰가 생긴다. 모르는 사람이어도 "깊게 팠구나"로 읽힌다.

---

### 4장. 결과 ① 정상 부하

**말할 것**

> "예상 정상 부하인 동시 사용자 100명 구간에서는 모든 API가 목표 응답시간 안에 처리됐습니다. 실패율은 X% 였습니다."

**보여줄 것** — 숫자 3개면 충분하다.

| 지표 | 결과 |
| --- | ---: |
| 처리량 | 초당 N건 |
| 조회 p95 | N ms |
| 실패율 | N % |

30초 안에 넘어간다. **여기는 "잘 됐다"는 확인일 뿐 발표의 핵심이 아니다.**

---

### 5장. 결과 ② 한계 지점 ★★

**발표의 중심.** 계단식으로 부하를 올리며 어디서 꺾였는지 보여준다.

**보여줄 것 — 그래프 1개**

```
가로축: 동시 사용자 (100 → 200 → 300 → 400 → 500)
세로축: p95 응답시간 (ms)

  p95
   ↑
   │                                    ●  ← 급격히 상승
   │                             ●
   │        ●      ●      ●
   └────────────────────────────────────→
          100    200    300    400    500
                                ↑
                          여기가 한계
```

**실패율을 같은 그래프에 겹쳐 그리면 더 좋다.** 응답시간이 오르는 지점과 실패가 시작되는 지점이 같은지 다른지가 한눈에 보인다.

**말할 것**

> "100명에서 300명까지는 응답시간이 거의 평평했습니다. 400명 구간에서 p95가 X ms에서 Y ms로 뛰었고, 실패율도 이때부터 올라갔습니다.
> **그래서 현재 구성의 한계는 약 350~400명 사이입니다.**
> 원인을 보니 (DB 연결 수 / CPU / Queue 적체) 가 먼저 한계에 도달했습니다."

**중요** — "500까지 버텼습니다"로 끝나면 안 된다. 그건 **한계를 못 찾은 것**이다. 그 경우 정직하게 말한다.

> "500명까지는 이상이 없었습니다. 한계를 찾지 못했다는 뜻이라, 800명까지 올려 재측정했습니다."

---

### 6장. 발견한 문제 ★★

**두 번째 하이라이트.** 여기서 "실제로 파봤구나"가 증명된다.

**하나만 깊게 말한다.** 테이블 해제 지연을 추천한다.

**말할 것**

> "테스트 준비 중에 코드를 읽다가 하나 발견했습니다.
>
> 손님이 나가고 직원이 '주문 완료'를 눌러도, **그 테이블에 다음 주문이 바로 안 들어갑니다.** 평균 15초, 최대 30초 막힙니다.
>
> 원인은 테이블 해제를 30초 주기 스케줄러가 처리하는데, **동기 시도가 없어서 첫 해제도 그 주기를 기다린다**는 점이었습니다. 같은 프로젝트의 다른 스케줄러는 전부 1초입니다.
>
> 설정 키 이름이 `release-retry-delay`, 즉 **재시도 간격**입니다. 재시도용으로 넣은 값이 평상시 지연으로 쓰이고 있었습니다.
>
> 개선안은 두 가지입니다. 주기를 1초로 맞추거나, 완료 시점에 한 번 동기 시도하고 실패했을 때만 스케줄러에 맡기는 것입니다."

**보여줄 것**

스케줄러 비교표. 이거 하나면 설명이 필요 없다.

| 스케줄러 | 주기 |
| --- | ---: |
| AuditOutboxScheduler | 1초 |
| QueueOrderOutboxPublisher | 1초 |
| **TableReservationReleaseRecovery** | **30초** |

**왜 강력한가**

- 부하 테스트를 **돌리기 전에** 발견했다 → 코드를 실제로 읽었다는 증거
- 성능 문제가 아니라 **사용자 경험 문제**를 찾았다 → 제품 관점이 있다
- 개선안이 구체적이다 → 말만 하는 게 아니다

---

### 7장. 개선 후 재측정

**있으면 최고, 없으면 통째로 생략한다.**

발표 전에 30초 → 1초만 바꿔서 다시 돌릴 수 있다면 반드시 한다. **설정값 한 줄이라 30분이면 된다.**

**보여줄 것** — before / after 나란히

| | 개선 전 | 개선 후 |
| --- | ---: | ---: |
| 테이블 재사용까지 | 평균 15초 | 1초 미만 |
| 매장 주문 처리량 | 초당 N건 | 초당 M건 |

**말할 것**

> "설정값 한 줄을 바꾸고 다시 측정했습니다. 매장 주문 처리량이 N배 올라갔습니다."

**"문제를 찾았다"보다 "찾아서 고쳤고 수치로 확인했다"가 훨씬 세다.** 발표 완성도가 한 단계 올라간다.

---

### 8장. 정리

0번에서 정한 한 문장을 그대로 다시 말한다.

> "포장 주문 기준 초당 N건까지 처리했고, 다음 병목은 테이블 예약이며, 원인과 개선안까지 확인했습니다."

여기에 한 줄 덧붙이면 좋다.

> "남은 과제는 (조리 흐름 검증 / 더 높은 구간 측정) 입니다."

**남은 과제를 스스로 말하는 것이 감점이 아니라 가점이다.** 다 했다고 하면 안 물어볼 질문도 물어보게 된다.

---

## 3. 그래프는 3개면 충분하다

| # | 그래프 | 쓰는 곳 | 없으면 |
| ---: | --- | --- | --- |
| 1 | **부하 단계별 p95 + 실패율** | 5장 | 발표가 성립 안 됨 |
| 2 | 시간에 따른 응답시간 (Soak) | 4장 | 생략 가능 |
| 3 | before / after 비교 | 7장 | 생략 가능 |

**1번은 반드시 만든다.** 나머지는 시간 남으면.

**만드는 법** — k6 결과를 `--summary-export` 로 JSON 저장했다면 단계별 p95를 뽑아 엑셀에 붙여 꺾은선으로 그리면 된다. 그래프 도구를 새로 배울 필요 없다.

**주의** — k6 터미널 출력 화면을 그대로 캡처해서 붙이지 않는다. 글씨가 작고 정보가 너무 많아 아무도 못 읽는다.

## 4. 예상 질문과 답변

**Q. 왜 500명으로 잡았나요?**

> "매장 100곳이 동시에 피크인 상황에 해당합니다. POS·키오스크·주방을 합치면 매장당 5개 세션 정도라, 500이면 100개 매장입니다. 1년차 목표 규모에 맞춰 잡았고, 실측 후 조정할 수 있게 설정값으로 뺐습니다."

*(팀 목표 매장 수를 미리 확인해두면 더 좋다)*

**Q. 실제 서비스랑 다르지 않나요?**

> "맞습니다. 운영 데이터가 없어서 실제 트래픽 패턴은 재현할 수 없습니다. 대신 매장 업무 흐름을 시나리오로 옮기고, 목표치를 정해 거기까지 올려보는 방식을 택했습니다. 실제 데이터가 쌓이면 비율을 조정할 계획입니다."

**Q. 매장 주문은 왜 뺐나요?**

> "테이블이 처리량 상한을 만들기 때문입니다. 테이블 하나에 주문 하나만 들어가고, 해제까지 30초가 걸려서, 섞어 돌리면 서버 성능이 아니라 테이블 회전율을 재게 됩니다. 그래서 분리해서 측정했습니다."

*(이 답변 자체가 이해도를 보여준다. 좋은 질문을 받은 것이다.)*

**Q. 테스트 환경이 운영이랑 같나요?**

> "아닙니다. 개발 환경이라 사양이 낮습니다. 그래서 절대 수치보다 **어디가 먼저 막히는지**에 초점을 뒀습니다. 병목의 종류는 환경이 달라져도 대체로 유지됩니다."

**Q. 그래서 실제로 몇 명 쓸 수 있는 건가요?**

> "이 환경 기준 N명입니다. 운영 환경은 사양이 다르므로 배포 후 같은 스크립트로 다시 측정할 계획입니다. 스크립트가 저장소에 있어서 주소만 바꾸면 바로 돌아갑니다."

## 5. 하지 말 것

**"통과했습니다"로 끝내기**

한계를 못 찾았다는 뜻이다. 반드시 어디서 꺾였는지까지 간다.

**시나리오 10개를 하나씩 다 설명하기**

지루하고 시간도 없다. 4종류로 묶어서 넘기고, 결과에 시간을 쓴다.

**터미널 출력 캡처 붙이기**

안 읽힌다. 숫자를 뽑아서 표나 그래프로 만든다.

**문제를 숨기기**

발견한 문제는 **성과지 흠이 아니다.** 오히려 "문제가 하나도 없었습니다"가 의심을 산다.

**모르는 걸 아는 척하기**

> "그 부분은 측정하지 못했습니다. 다음 과제로 두고 있습니다."

이게 훨씬 낫다. 어설프게 답하면 꼬리질문에서 무너진다.

## 6. 발표 전 체크리스트

| # | 항목 | 상태 |
| ---: | --- | :---: |
| 1 | 시나리오 10(한계 탐색) 최소 1회 실행 | ☐ |
| 2 | 단계별 p95 그래프 1장 완성 | ☐ |
| 3 | 한계 지점 숫자 확정 (몇 명에서, 무엇 때문에) | ☐ |
| 4 | 테이블 30초 이슈 팀 확인 완료 | ☐ |
| 5 | (가능하면) 개선 후 재측정 | ☐ |
| 6 | 목표 매장 수 확인 — "왜 500명?" 대비 | ☐ |
| 7 | 발표 한 문장 확정 | ☐ |

**1·2·3번이 없으면 5장을 채울 수 없다.** 다른 걸 다 미루더라도 이건 한다.

**4번은 안 되면 "확인 중"이라고 해도 된다.** 발견했다는 사실 자체가 성과다.

---

## 7. 시간이 없다면

발표 준비 시간이 부족할 때 우선순위.

```
1순위  시나리오 10 한 번 돌리고 그래프 1장     ← 이것만은 반드시
2순위  테이블 30초 이슈 정리 (이미 다 되어 있음)
3순위  3장(신뢰성 확보) 슬라이드
```
